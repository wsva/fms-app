# Release Download Proxy Design v1 (no-store edition)

Working blueprint for serving FmS release downloads from the website
(lusworkshop.site) **without ever storing packages on the web server**: when a
visitor clicks download, the website fetches the package from GitHub Releases
and streams it through. Motivated by the decision (October 2026) that GitHub
stays the single download source for security reasons — the website must not
become a second place where installers live and can be silently replaced.

Nothing here is implemented yet. The shelved alternative (cron mirror + local
storage + updater fallback endpoint) is preserved on the `release-mirror`
branches of `wsva/fms-app` and `wsva/fms`; this doc supersedes its *serving*
half with a lower-risk shape. Implement only when the download page needs to
serve users who cannot reach GitHub themselves.

---

## 1. Where we are today

- `build.yml` publishes every installer as a GitHub Release asset
  (`FmS_<platform>_<arch>_<ref>.<ext>`); `releases/latest` is the canonical feed.
- The website (`learning/fms`, deployed from `wsva/fms_build`) renders the
  landing download cards server-side: `src/lib/github-release.ts` fetches the
  GitHub Releases API (1 h cache), `pickAsset()` chooses per platform, the card
  links straight to `browser_download_url` — the user's browser talks to GitHub.
- The in-app updater reads
  `https://github.com/wsva/fms-app/releases/latest/download/latest.json`
  (single endpoint) and verifies each download against the minisign pubkey
  pinned in `tauri.conf.json`.

Consequence: a visitor who cannot reach `github.com` cannot install or update,
and a hacked web server today can change nothing (it serves no bytes).

## 2. Goals / non-goals

**Goals**

- A browser user downloads the *authentic GitHub bytes* while talking only to
  `lusworkshop.site` (server can reach GitHub even when the user cannot).
- No package bytes at rest on the web server — nothing to tamper with between
  releases, nothing to clean up, no retention policy.
- Resumable downloads (HTTP Range) and honest metadata (version, file size).

**Non-goals**

- **Not** a protection against a fully rooted server (see §4 — the remaining
  threat needs OS code signing to close; out of scope here).
- **Not** an update channel: the desktop updater stays GitHub-only by explicit
  decision. This design changes only what the *download page* offers.
- **Not** a general-purpose GitHub proxy. See §6.1 — the handler is a
  whitelist, not a fetch-any-URL endpoint.

## 3. Why "no-store proxy" is stronger than "mirror"

With a mirror, a hacked web server needs no further exploit: evil files land on
its own disk and are served to everyone from then on. The compromise is
*persistent and automatic*.

With a proxy, the server holds no package bytes at all. Each download is
re-fetched live over TLS with GitHub's certificate validated **by the server
itself**. To poison a user, an attacker who owns the server must additionally
tamper with its own process' outbound request path (intercept before it leaves,
or swap after it arrives in memory). That is possible under full compromise,
but it is no longer the free outcome of owning the web root.

Trust chain per download:

```
browser ──HTTPS (server's cert)──▶ web server ──HTTPS (GitHub's cert)──▶ GitHub CDN
```

Each link is authenticated by a party the previous link's compromise does not
control. The weakest remaining link is "the server lies to the browser about
everything it renders" — which no server-side measure can fix; only
verification that happens on the user's machine can (§9).

## 4. Threat model, stated honestly

| Attacker owns | Direct-GitHub (today) | Mirror (shelved) | Proxy (this doc) |
|---|---|---|---|
| github.com DNS/TLS only | user harmed | user harmed | user harmed |
| Web server (web root / app code) | **safe** — server serves no bytes | **all future downloads poisoned** | live stream tampered only while running; nothing at rest to swap |
| Web server (full root, incl. process memory) | safe | poisoned | **poisoned** — server sits in the middle of its own request |
| Signing key (`TAURI_SIGNING_PRIVATE_KEY`) | updater poisoned | everything poisoned | updater poisoned |

The row that this design improves over the mirror is row 2: a defacement-class
compromise, the most likely kind. Row 3 is the residual risk, and its real fix
is Windows EV code signing + macOS Developer ID/notarization, where the OS on
the *user's* machine verifies the bytes — a channel the hacker cannot reach.
Android already has this property via the APK keystore signature.

Also unchanged: browser users cannot check a published checksum meaningfully,
because the page printing the checksum is generated by the same server that
could tamper. Show `size` (it costs nothing and catches corruption), but do
not pretend the checksum line is a defense.

## 5. Architecture

One new route in `learning/fms`, plus a small lib addition. No CI changes, no
server-side storage, no cron.

```
GET /download/<platform>                      # stable, user-facing (bookmarkable)
GET /download/<tag>/<asset-name>              # explicit version, for agents/docs
      │
      ▼  route handler (server)
1. resolve: latest release via GitHub API    (fetch cache: next:{revalidate:3600})
   or validate <tag>/<asset-name> against §6.1 grammar
2. pick:    pickAsset(assets, <platform>)    (reuse lib/github-release.ts matcher)
3. stream:  fetch(browser_download_url)      (GitHub 302s to its CDN; Node fetch follows)
      │     forward:  Range                  → relay: 206, Content-Range,
      │     Accept-Ranges, Content-Length back as-is
      ▼
   Response  ◀── upstream body piped through (never buffered whole, never written)
   + Content-Disposition: attachment; filename=...
   + Cache-Control: no-store                (§7 — decide before enabling any cache!)
```

Landing cards change one line: `href` becomes `/download/windows` etc. The
"or download from GitHub" direct link stays visible beside every card — if the
proxy fails (server can't reach GitHub either), the page still tells the truth
about where the files live.

The route must not buffer installers: read the upstream as a byte stream
(`Readable.fromWeb`) and hand it to the `Response`; a 150 MB installer must
never exist whole in the Node process' memory.

## 6. Correctness and safety rules

### 6.1 Whitelist — the security-critical part

The handler accepts **only**:

- platform tokens `windows | linux | android` on the `/download/<platform>`
  form, resolved server-side against the latest release; and
- `<tag>/<name>` pairs where `<tag>` is a `v*.*.*` tag of **`wsva/fms-app`
  specifically** and `<name>` matches `^FmS_[A-Za-z0-9._+-]+\.(exe|AppImage|deb|rpm|dmg|apk|ipa)$`
  **and appears in that tag's asset list from the API** (not just the grammar).

Everything else is a 404, and the handler never accepts a URL, host, repo or
path fragment from the request. A generic "fetch this GitHub URL" endpoint is
an open proxy: traffic laundering, backend hammering, and exfiltration through
your domain — plus one SSRF line item for every future redirect quirk. The
asset-list membership check is the load-bearing step: names are validated
against what GitHub actually published for that tag.

### 6.2 Never trust user input into the upstream request

The upstream URL is always taken from the GitHub API response
(`browser_download_url`), never assembled from request bytes. The user picks a
platform or a (validated) tag; the server asks GitHub what the file is.

### 6.3 Range relay, not Range emulation

Forward the `Range` header verbatim and pass through whatever the CDN answers
(200 vs 206, `Content-Range`). Do not implement range logic in the handler —
GitHub's asset storage supports ranges natively, and re-deriving it invites
off-by-one corruption of exactly the resumed downloads this feature exists for.

### 6.4 TLS to the user

The whole premise assumes browser→server is HTTPS (HSTS on, no cert warnings
"temporarily disabled for testing"). A network attacker who can strip that
makes the proxy worse than a direct GitHub link, not better.

## 7. Costs and mitigations

| Cost | Reality | Mitigation |
|---|---|---|
| Bandwidth ×2 per download, forever | every byte flows GitHub→server→user; ~150 MB installers | count it in the hosting bill; `no-store` (default) makes this exact |
| Latency / time-to-first-byte | one extra hop + redirect chase | start streaming immediately; no auth walls on the route |
| Server must reach GitHub | if the *server* is also blocked, the proxy answers nothing | keep the direct-GitHub link visible; this design helps the "user blocked, server free" case only |
| API rate limit (60/hr unauthenticated per source IP) | only the latest-release resolve hits it; assets themselves are not API-metered | 1 h ISR cache; a fine-grained public-read token if traffic grows |
| Long connections hog | 10 concurrent installers ≈ sustained megabytes/s for minutes | Node streams handle it; keep an eye on pod CPU/mem limits; `terminationGracePeriodSeconds` so restarts don't cut mid-stream users silently |
| DoS amplification | attacker triggers *you* to fetch from GitHub repeatedly | whitelist (§6.1) + the API cache bounds upstream fetches per release, not per user |

If volume ever justifies a caching layer (CDN in front of `/download/...`),
that cache is storage with a different owner — the no-store property of this
design dies the moment `Cache-Control` says anything but `no-store` somewhere
upstream. Decide consciously; a CDN that only caches *after* validating against
the origin's whitelist is still better than server-side disk (the mirror),
because tampering requires the CDN's keys too, not just the web host's.

## 8. Delta from `release-mirror` (shelved branches)

Reuses from that branch's work: the download-card plumbing (asset field
normalization, `pickAsset` untouched because names are preserved upstream),
the `Content-Disposition`/Range response-shape code in the mirror route, and
the i18n rewording pattern.

Drops entirely: `scripts/mirror_releases.py` (cron), the hostPath volume +
`deployment.yaml` changes, `releases.json`, the rewritten mirror-variant
`latest.json`, the second updater endpoint in `tauri.conf.json`, the
`ENDPOINT_TIMEOUT` change, and the SHA-256 display on cards (§4: honest
checksums can't come from the proxying server either — but they also come
cheaper from GitHub's own release page than from our server's disk).

Net new: one route handler + ~20 lines of lib/landing changes.

## 9. Open questions to settle before implementing

1. **Does the server actually reach GitHub freely?** (Deployment is a K8s pod
   on the home node — verify outbound to `api.github.com` and
   `objects.githubusercontent.com` without the proxy the laptops need.)
   If it doesn't, this design is decorative and §1's status quo is equivalent.
2. **Code signing purchase decision** (Windows EV + Apple Developer ID): the
   real closure of row 3 in §4. When bought, update `build.yml` and *then*
   reconsider the mirror/updater-fallback branch for reachability, since
   tamper-evidence then travels with the file, not the channel.
3. **Do we want `/download/latest.json` proxied too** so docs/agents have one
   domain for everything? Harmless with the whitelist; the updater itself still
   must not be pointed here without revisiting the decision that GitHub stays
   the single update source.
4. **Retention of the explicit `<tag>/<name>` form**: proxying any *past* tag
   means the site permanently fronts GitHub's whole release history for that
   repo. Probably fine; if not, restrict to the latest N tags resolved via API.
5. **Metrics**: a download counter per platform token would answer "is this
   channel actually used by blocked users, or paying double bandwidth for
   nobody?" — worth 10 lines before committing to the bandwidth cost.
